# Архитектура

Документ по разделу 4 ТЗ: пайплайн и границы слоёв — парсинг, генерация, вёрстка, аудит, экспорт.
Запуск и переменные окружения — в [README](README.md), модели — в [MODELS.md](MODELS.md),
проверки аудита и автотесты — в [AUDIT.md](AUDIT.md).

## Принципы

1. **Шаблон — набор правил, а не картинка.** Дизайн корпоративного шаблона живёт в основном в
   слайдах-примерах, а не в макетах: в VK Tech 36 из 54 слайдов лежат на одном «свободном» макете и
   нарисованы фигурами. Парсер разбирает каждый слайд-пример в **паттерн** со слотами (заголовок,
   тезисы, карточки, показатели, этапы, место под картинку), а сборка клонирует подходящий пример и
   заполняет его слоты. Новые слайды выглядят как сам шаблон, и ничего не зашито под три шаблона кейса:
   любой загруженный файл проходит тот же разбор.
2. **Модель пишет содержание, код верстает.** LLM отвечает за план колоды и тексты. Подбор паттерна,
   визуализация данных, сборка .pptx и детерминированные проверки — правила в коде и YAML. Поэтому
   вёрстка воспроизводима, а её ошибки ловит аудит.
3. **У каждого шага с моделью есть путь без неё.** Модели нет, она не ответила или вернула мусор —
   стадия деградирует, а не падает: колода собирается из тезисов брифа, паттерны размечаются правилами,
   контекстуальные проверки идут по запасным правилам, слайд без картинки верстается тезисами.
4. **Промпты и параметры — в файлах с версиями.** Скиллы и агенты лежат в `backend/skills/*.yaml`,
   прогон генерации сохраняет снимок их версий.
5. **Один контракт слайда.** Модель `Slide` (`backend/app/schemas/slide.py`) — общий язык генерации,
   вёрстки, экспорта, аудита и редактора. Слои обмениваются только ею и описанными ниже структурами.

## Сервисы

| Сервис | Роль |
|---|---|
| `frontend` | React + TypeScript (Vite), nginx: интерфейс, проксирует `/api` на бэкенд |
| `backend` | FastAPI: REST и SSE, экспорт, рендер по запросу пользователя, шрифты шаблонов для превью |
| `worker` | arq: разбор шаблонов, пайплайн генерации (до 4 одновременно), перерендер вариантов, догоняющий аудит |
| `db` | PostgreSQL 16: шаблоны, презентации, прогоны, варианты, замечания аудита |
| `redis` | сессии, очередь задач, прогресс генерации (pub/sub → SSE), heartbeat воркера |

Файлы — в томе `storage`: контент-пакеты, рендеры шаблонов и вариантов, пиктограммы шаблонов,
картинки пользователей и иллюстрации модели (`generated/<id презентации>/`).

## Пайплайн генерации

```
шаблон .pptx ─► 1 Декомпозиция шаблона ─► паттерны, макеты, токены дизайн-системы, рендеры
бриф, файлы ──► 2 Анализ контент-пакета ─► выдержки для промптов, фото для слайдов
                     │
                     ▼
               3 Генерация структуры ───► план: состав слайдов, типы, выводы, обязательные факты
                     ▼
               4 Тексты слайдов ────────► тексты под структуру вёрстки + редактура колоды
                     ▼
               5 Вёрстка трёх вариантов ► 3 × список Slide: у каждого слайда паттерн или макет шаблона
                     ▼
               6 Графики, таблицы, инфографика ► правила визуализации данных
                     ▼
               7 Генерация изображений ─► фото из материалов или иллюстрации в стиле шаблона
                     ▼
               8 Анимации и переходы ───► появление элементов по правилам типа слайда
                     ▼
               9 Сборка слайдов по шаблону ► .pptx трёх вариантов, превью, факты для аудита
                     ▼
              10 Аудит ─────────────────► 34 проверки: по данным, по рендеру, моделью-судьёй
```

| № | Стадия | Код | Скиллы (YAML) | Модель | Без модели |
|---|---|---|---|---|---|
| 1 | Декомпозиция шаблона | `pipeline/parsing/`, `pipeline/ai/vlm.py`, `services/templates.py` | `template_parser` | VLM, необязательно | разметка паттернов правилами |
| 2 | Анализ контент-пакета | `pipeline/content/` | `content_analyzer` | VLM для картинок, необязательно | описание фото по имени файла |
| 3 | Генерация структуры | `pipeline/planning/planner.py`, `outline.py` | `outline_planner` | LLM | план из тезисов брифа |
| 4 | Тексты слайдов | `planning/writer.py`, `deck_editor.py`, `typography.py`, `budgets.py` | `slide_writer`, `deck_editor` | LLM | факты плана как есть |
| 5 | Вёрстка трёх вариантов | `pipeline/layout/composer.py`, `matcher.py`, `fitting.py` | `layout_composer`, `slide_editor` | LLM — только сокращение текста под слоты | без сокращения |
| 6 | Графики, таблицы, инфографика | `pipeline/visuals/visualizer.py`, `numbers.py` | `visualizer` | — | — |
| 7 | Генерация изображений | `pipeline/visuals/illustrations.py`, `pipeline/ai/t2i.py`, `pipeline/content/image_matcher.py` | `image_style`, `image_director`, `image_generator` | VLM, LLM, FLUX.2 [klein] 4B | слайды «текст и изображение» — тезисами |
| 8 | Анимации и переходы | `pipeline/visuals/motion_rules.py`, `pipeline/export/motion.py` | — | — | — |
| 9 | Сборка слайдов по шаблону | `pipeline/export/`, `services/renders.py` | — | — | упрощённый рендер без LibreOffice |
| 10 | Аудит | `pipeline/audit/`, `services/audit.py` | `auditor` | судья: LLM и VLM | запасные правила для 4 проверок |

Стадии выполняет воркер (`pipeline/orchestrator.py`, список стадий — `pipeline/stages.py`). Каждая стадия
пишет в прогон время начала и конца и подпись с результатом (модель, запросы, токены, что сделано);
прогресс публикуется в Redis и приходит в интерфейс по SSE.

**Параллельность.** Работа, которая не зависит друг от друга, идёт одновременно:

- тексты слайдов пишутся параллельно, по запросу на слайд (`LLM_CONCURRENCY`);
- стиль иллюстраций шаблона считается в фоне с начала прогона;
- картинки рисуются, пока текст подгоняется под слоты и строятся визуализации. Генерация ждёт их не
  дольше `T2I_WAIT_SECONDS` с начала рисования: зависший запрос провайдера не выводит колоду за 5 минут,
  а слайд без картинки верстается тезисами;
- три варианта рендерятся двумя процессами LibreOffice (`RENDER_CONCURRENCY=2`): примерно на 40% быстрее
  одного процесса, больше двух не ускоряет — сборка .pptx упирается в Python;
- модель-судья читает тексты колод, пока LibreOffice собирает превью, а картинки проверяет сразу после
  рендера. Генерация ждёт судью не дольше `AUDIT_WAIT_SECONDS`; опоздавшие вердикты догоняет фоновая
  задача, отчёт аудита обновляется сам.

**Несколько генераций сразу.** Воркер выполняет до 4 генераций одновременно, у каждой свои потоки запросов
к модели. Чтобы генерации не делили лимит одного API-ключа провайдера, ключей может быть несколько
(через запятую в `LLM_API_KEY` и других `*_API_KEY`): каждый запрос уходит на наименее загруженный ключ
(`pipeline/ai/keys.py`), ключ с ответом 429 или 401–403 на время выводится из оборота. Общим остаётся
только рендер: процессов LibreOffice не больше `RENDER_CONCURRENCY` на воркер.

**Время.** На шаблоне VK Tech (10 слайдов, Qwen3.8-27B через RouterAI) три варианта собираются за
162–217 с без иллюстраций и за 211–249 с с ними. Больше всего времени занимают тексты (30–75 с в
зависимости от `LLM_CONCURRENCY`) и рендер превью в LibreOffice. Заметный разброс даёт провайдер
модели: один повторный запрос плана добавляет до минуты, поэтому итоговые замеры надо делать на целевом
хосте с тем эндпоинтом модели, который будет в работе.

## Границы слоёв

### Парсинг — `pipeline/parsing/`, `pipeline/ai/vlm.py`

- **Вход:** файл шаблона. `.pptx`, `.potx`, `.pptm`, `.potm`, `.ppsx`, `.ppsm` читаются напрямую
  (`parsing/formats.py`), `.ppt`, `.pot`, `.pps`, `.odp`, `.otp` конвертирует LibreOffice.
- **Выход:** запись `Template`: `layouts` и `layout_roles` (макеты и их назначение), `tokens` (тема,
  фактическая палитра, шрифты, типографическая шкала и стили ролей, сетка и поля, колонтитулы и логотипы,
  стиль таблиц и цвета рядов диаграмм, фоны, библиотека пиктограмм, стиль иллюстраций), `patterns`
  (слоты с ролями и ёмкостью в знаках, элементы серий, привязанный к слотам декор, место под картинку,
  тип и назначение слайда), рендеры слайдов-примеров и макетов.
- **Граница:** парсер не знает о контенте. OOXML разбирается детерминированно; VLM видит рендер слайда
  и только уточняет тип, назначение и роли, ссылаясь на существующие id фигур (ответ проверяется схемой
  и порогом уверенности). Ошибка на одном слайде помечает этот слайд и не роняет разбор. Кэш разбора
  (`cache/`) применяется только к встроенным шаблонам — загруженный шаблон всегда разбирается целиком.

### Генерация содержания — `pipeline/content/`, `pipeline/planning/`, `pipeline/ai/llm.py`

- **Вход:** название, назначение (фича, продукт, проект, инициатива), бриф, контент-пакет, настройки
  (число слайдов, язык, тон, аудитория), пользовательские скиллы и сводка возможностей шаблона — какие
  типы слайдов у него есть и сколько знаков помещается в их слоты (`planning/budgets.py`).
- **Выход:** план — список спецификаций слайдов: ссылка, тип, группа, приоритет, тема, вывод, факты,
  которые обязаны попасть на слайд, тексты сразу в нескольких формах (тезисы, карточки, колонки), данные
  для диаграммы, этапы, заметки докладчика. План хранится у прогона (`Generation.plan`): рерол варианта
  пересобирает вёрстку из него без новых запросов к модели.
- **Граница:** генерация не выбирает паттерны и не знает геометрии — только типы слайдов и бюджеты знаков.
  Ответы модели проверяются JSON-схемой и нормализуются; редактура колоды не может менять числа.

### Вёрстка — `pipeline/layout/`, `pipeline/visuals/`

- **Вход:** план, паттерны и макеты шаблона, ось вариантов.
- **Выход:** три `VariantDraft` со списками `Slide`: тип, тексты, данные визуализации, `pattern_id`
  (слайд-пример) или `layout_key` (макет), картинка.
- **Граница:** вёрстка не придумывает текст. Единственное обращение к модели — сокращение текста,
  который заметно длиннее слотов выбранного паттерна (`layout/fitting.py`), с теми же фактами.
  Файл шаблона вёрстка не трогает — только ссылается на его паттерны и макеты.

### Экспорт — `pipeline/export/`, `services/renders.py`, `services/export.py`

- **Вход:** список `Slide`, файл шаблона, тема и токены.
- **Выход:** `DeckBuild` — .pptx с нативными объектами (клоны слайдов-примеров с заполненными слотами,
  слайды на макетах: текст, диаграммы, таблицы, фигуры, картинки, анимации и переходы), рамки элементов
  для подсветки замечаний и редактора и факты по каждому слайду: строки текста PDF-рендера, шрифты, кегли,
  цвета, картинки (в том числе в плейсхолдерах) и логотипы. PDF и HTML собираются из того же .pptx через
  LibreOffice. Новый текст на макетах получает гарнитуры заголовков и основного текста шаблона.
- **Граница:** превью в интерфейсе, PDF и HTML — рендеры того же файла, который скачивает пользователь.
  Растровых слайдов нет, это проверяет аудит (`integrity.raster_slide`). Приближённое HTML-превью редактора
  рисуется теми же файлами шрифтов, что и LibreOffice: `services/fonts.py` находит их через fontconfig и
  отдаёт браузеру как `@font-face` (`/api/fonts/css`).

### Аудит — `pipeline/audit/`, `services/audit.py`

- **Вход:** слайды варианта, шаблон и его токены, факты рендера, бриф и материалы, вердикты судьи.
- **Выход:** замечания с адресом элемента на слайде, степенью и способом исправления; отчёт по всем
  проверкам с их состоянием (выполнена, ждёт рендера или судью, запасное правило).
- **Граница:** аудит не зависит от генерации и проверяет любые слайды — после ручной правки, рерола,
  чата. Исправления идут через те же функции, что и генерация: правка слайда моделью
  (`planning/editor.py`), перевёрстка (`layout/composer.py`). Подробнее — [AUDIT.md](AUDIT.md).

### Оркестрация и приложение

- `pipeline/orchestrator.py` — стадии, прогресс, время, heartbeat, фоновые задачи прогона;
  `pipeline/jobs.py` и `worker.py` — задачи arq: разбор шаблона, генерация, перерендер варианта,
  догоняющий аудит. Генерация не перезапускается сама (`max_tries=1`): если воркер перезапустился или
  машина уснула посреди прогона, вторая попытка поверх первой дала бы дубли вариантов. Зависший прогон
  по отсутствию heartbeat помечается ошибкой, и пользователь запускает генерацию заново.
- `services/` — операции поверх БД (шаблоны, аудит, рендеры, экспорт, иллюстрации, скиллы, совместная работа).
- `api/routes/` — REST и SSE; `frontend/src/` — интерфейс.

## Три варианта вёрстки (ТЗ, п. 5)

Варианты различаются по одной оси, которую пользователь выбирает перед генерацией (по умолчанию —
плотность). Ось задаёт **профиль** варианта (`skills/layout_composer.yaml`): сколько тезисов оставить,
заголовки-выводы или темы, как показывать данные (диаграмма, KPI, таблица), как верстать гибкие тезисы
(список, карточки, колонки, текст с иллюстрацией) и порядок слайдов. Кроме профиля варианты A, B и C
берут разные паттерны из равноценных кандидатов, а рерол — случайный из более широкого круга.

| Ось | A | B | C |
|---|---|---|---|
| Плотность контента | Лаконичный: карточки, KPI | Сбалансированный: до 5 тезисов, диаграммы, колонки | Подробный: развёрнутые тезисы и таблицы |
| Способ визуализации данных | Диаграммы | KPI-инфографика | Таблицы |
| Порядок и группировка слайдов | Линейный рассказ | Сначала вывод | По разделам, с разделителями |
| Выбор макетов | Текстовые макеты | Карточки и колонки | Текст и изображение (без картинок — колонки и показатели) |

Почему эти оси:

- **Это решения, которые дизайнер принимает при вёрстке одной колоды:** сколько текста оставить на
  слайде, в какой форме показать числа, в каком порядке рассказывать, какими макетами шаблона
  пользоваться. Пользователь выбирает, какое из них он хочет сравнить.
- **Смысл одинаковый, подача разная.** Все варианты собираются из одного плана и одних фактов: модель
  пишет содержимое гибкого слайда сразу в трёх формах, поэтому варианты различаются вёрсткой, а не
  тем, что на них написано.
- **Одинаковое соответствие шаблону.** Каждый слайд любого варианта собран из паттернов и макетов того же
  шаблона и проходит один и тот же аудит. Заголовки-выводы есть у всех вариантов: различие не покупается
  ценой качества.
- **Визуальная различимость** обеспечена формой контента (карточки, колонки, диаграммы, таблицы, KPI) и
  разными паттернами шаблона.

## Визуализация внутри слайда (ТЗ, п. 3 и 3.1)

- **Диаграммы** — нативные диаграммы PowerPoint. Если у шаблона есть слайд-пример с диаграммой нужного
  типа, копируется она со стилями, а данные заменяются. Иначе создаётся новая в цветах рядов шаблона.
  Тип диаграммы по данным, сортировку, акцент на ключевой категории, округление и подписи задают правила
  `skills/visualizer.yaml`.
- **Таблицы** — нативные, в стиле таблиц шаблона.
- **Инфографика** — KPI, этапы, карточки, колонки, сравнения: нативные фигуры слайдов-примеров шаблона
  с заполненными слотами.
- **Схемы вместо объектов SmartArt.** Объект SmartArt (части `dgm*` в .pptx) мы осознанно не создаём:
  LibreOffice, на котором построены превью и PDF, рисует его не так, как PowerPoint, а при правке
  PowerPoint пересобирает раскладку по своим правилам и теряет оформление шаблона. Схемы процессов, этапов
  и сравнений строятся нативными фигурами по паттернам шаблона — они редактируются в PowerPoint и
  выглядят одинаково во всех форматах экспорта.
- **Пиктограммы.** Библиотека пиктограмм шаблона извлекается при разборе (`tokens.icons`, страница
  шаблона). На слайдах, собранных по паттернам, иконки остаются декором, привязанным к своим слотам
  (у карточек, строк, показателей), и удаляются вместе с незаполненным слотом. Новые пиктограммы сервис
  не рисует.
- **Иллюстрации** (п. 3.1) — стадия «Генерация изображений»:
  1. Фото из контент-пакета подбираются к слайдам по смыслу (`content/image_matcher.py`).
  2. Стиль иллюстраций шаблона: VLM смотрит на слайды-примеры с картинками и описывает материал, свет
     и типичные объекты; фон берётся из фона контентных слайдов, цвета — из палитры. Описание
     сохраняется в дизайн-системе шаблона и считается один раз.
  3. Одна картинка на слайд плана — общая для трёх вариантов; пропорции — по рамке картинки паттерна.
  4. Арт-директор (LLM) одним запросом придумывает сюжеты для всех слайдов: узнаваемый предмет по смыслу
     слайда, без экранов, документов и надписей.
  5. FLUX.2 [klein] 4B рисует картинки параллельно, с фиксированным сидом.
  6. Картинка встаёт на место фото слайда-примера: рамка, маска, скругление и эффекты шаблона
     сохраняются. Паттерн, где текст лежит на фото, для такой картинки не выбирается. На макете
     картинка стоит справа от текста.
  7. Картинка не получилась — слайд верстается тезисами, пустых рамок на слайде нет.

## Анимации и переходы

Стадия «Анимации и переходы» (`pipeline/visuals/motion_rules.py`) расставляет анимации появления правилами
по типу слайда, без модели: это оформление, а не содержание. Элементы появляются сами по очереди
(без кликера), длинные списки — одним блоком, заголовок открывается вместе со слайдом, скрытые элементы
пропускаются, анимации, заданные пользователем, не перезаписываются. Режим — в настройках генерации:
сдержанные, живые или без анимаций. Те же правила работают в реролле, в слайде по описанию и по кнопке
«Автоанимации» в Студии; в .pptx уходят нативные эффекты PowerPoint (`export/motion.py`).

## Устойчивость и работа с неопределённостью

- **Незнакомый шаблон:** полный разбор (формат → OOXML → паттерны → рендер → VLM) без кэша. Слайд, который
  не разобрался, в генерацию не идёт; слайду без подходящего паттерна достаётся макет шаблона; роли
  макетов определяются по использованию, плейсхолдерам и названиям.
- **Ответы моделей:** запрос идёт лестницей форматов (`json_schema` → `json_object` → без формата), сбои
  связи и ответы 429/5xx повторяются, «рассуждения» вместо JSON — повтор без схемы, план заметно короче
  запрошенного — повторный запрос. Ответ не той формы (число или список вместо объекта, словарь вместо
  списка) не роняет генерацию: слайд остаётся с фактами плана. Вердикты судьи кэшируются по отпечатку
  слайда: после правки проверяется только изменённое.
- **Провайдер моделей:** при нескольких API-ключах отказ одного ключа (лимит, баланс, доступ) — сразу
  повтор на другом; картинки ограничены сроком `T2I_WAIT_SECONDS`, судья — `AUDIT_WAIT_SECONDS`
  (опоздавшие вердикты догоняет фоновая задача).
- **Факты:** план требует обязательные факты на слайде, редактура колоды не может менять числа, аудит
  сверяет цифры с материалами, слайд по описанию в Студии берёт числа только из описания, брифа и
  материалов.
- **Шрифты:** доступность гарнитур шаблона для рендера проверяется при разборе; фирменные шрифты кладутся
  в `backend/fonts/`.

## Версионирование скиллов и агентов (ТЗ, п. 4)

Промпты, схемы ответа и параметры не зашиты в код — они лежат в `backend/skills/*.yaml`, у каждого файла
есть версия:

| Файл | Тип | Исполнитель | Стадия |
|---|---|---|---|
| `template_parser.yaml` | skill | код + VLM | декомпозиция шаблона |
| `content_analyzer.yaml` | skill | код | анализ контент-пакета |
| `outline_planner.yaml` | agent | LLM | генерация структуры |
| `slide_writer.yaml` | agent | LLM | тексты слайдов |
| `deck_editor.yaml` | agent | LLM | тексты слайдов (редактура колоды) |
| `layout_composer.yaml` | skill | код | вёрстка трёх вариантов |
| `visualizer.yaml` | skill | код | графики, таблицы, инфографика |
| `image_style.yaml` | agent | VLM | генерация изображений (стиль шаблона) |
| `image_director.yaml` | agent | LLM | генерация изображений (сюжеты) |
| `image_generator.yaml` | skill | text-to-image | генерация изображений |
| `auditor.yaml` | agent | LLM + VLM | аудит (каталог проверок, промпты судьи) |
| `slide_editor.yaml` | agent | LLM | правка слайда из чата, автоисправления аудита, сокращение под слоты |

Каждый прогон генерации сохраняет снимок версий всех скиллов (`Generation.skills`), он показан на экране
генерации. Пользовательские скиллы (свои правила текста и оформления) хранятся в библиотеке с историей
версий, стандартные лежат в `backend/skills/presets/`; подключённые к презентации тоже попадают в снимок.
